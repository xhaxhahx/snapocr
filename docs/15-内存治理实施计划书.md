# SnapOCR 内存治理实施计划书

> 版本：2026-10-29 v1.0
> 场景约束：一台永不关机、本应用永不关闭、每天使用全部功能的固定性能电脑。
> 目标：**用户随时可用、完全无感**的前提下，把常驻内存钉在阈值内——
> **Commit ≤ 启动初始化基线 + 48MB**（"比刚初始化多几十MB顶多"），
> 且应用/系统总体运行不受本项目拖累。

---

## 1. 实测数据（本轮深挖，安装版真实会话）

| 实验 | Commit 变化 | 结论 |
|---|---|---|
| 启动初始化（托盘常驻，引擎未加载） | 263.8~265.8 MB | **基线** |
| 纯复制/遮罩会话 ×10（框选→复制→取消） | **+0.4MB/轮，平坦** | 遮罩/抓屏/工具条/剪贴板路径无泄漏（destroy 修复生效） |
| OCR 会话（真实识别） | **+13~38MB/轮，持续爬升** | 泄漏锁定在 OCR 路径 |
| OCR + 释放模型开关（true/false）两种配置 | 增速相同 | 与"是否释放"开关无关 → 另有机制 |
| 主题深浅切换 ×6 | 零增长 | 主题路径无泄漏 |
| 引擎就绪日志 vs 每轮 | release=true 时每轮重载；false 时部分轮仍重载 | 见根因 ①② |

## 2. 根因分析

1. **释放不回收（主因）**：`release_engine()` 只把模块级 `_engine` 置 None，
   **从不调用 `gc.collect()`**。RapidOCR/onnxruntime 会话对象进入 Python 分代垃圾
   缓冲，迟迟不析构 → 旧会话的 ~13MB 模型+arena 一直驻留；下一轮重新加载又开一份
   新会话 → **每轮净增一份模型内存**。恢复默认打开该开关的用户反而更糟。
2. **keep-loaded 模式 arena 增长**：不释放时 onnxruntime CPU arena 按历史出现过的
   张量形状保留峰值段；检测行/识别行的形状随内容变化，长周期下缓步增长（无硬上限）。
3. **（防御性）** 事件循环被长任务占住时，单实例转发 ack 超时（已修：3s+重试）；
   看门狗需要把"忙碌判定"做严，避免在会话中自愈。
4. 复制/遮罩/主题路径实测无泄漏，无需处理。

## 3. 治理架构：三层防线

```
┌─ L0 预防（写代码时就做对，已在历史轮完成）────────────────┐
│ 抓屏缓冲 release_buffers、遮罩 destroy()、钉住窗强引用+即时回收 │
└──────────────────────────────────────────────┘
┌─ L1 即时/软释放（零成本顺手做）──────────────────────┐
│ a. release_engine() 后强制 gc.collect()（修复根因1）          │
│ b. 会话结束：gc.collect() + QPixmapCache.clear()             │
│ c. 已关闭预览窗即时从 _previews 摘除（不等下一轮）            │
└──────────────────────────────────────────────┘
┌─ L2 内存看门狗（常驻兜底，保证硬上限）────────────────────┐
│ QTimer 60s 采样自身 Commit：                                 │
│  · 超过 基线+24MB（软阈值）且空闲 → 软释放：gc+QPixmapCache  │
│    +摘预览窗+**释放引擎**（空闲时重载 1.2s 用户无感）         │
│  · 连续 2 次超过 基线+48MB（硬阈值）且空闲 → **自愈重启**：   │
│    派生新进程(--hidden --resident --recycle) → 旧进程退出    │
│  · 基线取历史最低采样（防止阈值漂移）；≥1h 才允许再次重启     │
└──────────────────────────────────────────────┘
```

### 状态机（看门狗）

```
INIT --(启动45s后采样)--> ARMED(基线=历史最低Commit)
ARMED --(Commit>软阈值 且 idle)--> SOFT_RELEASED（执行软释放，重新采样）
SOFT_RELEASED/ARMED --(连续2次 Commit>硬阈值 且 idle 且 距上次重启≥1h)--> RECYCLE
RECYCLE --(派生新进程+quit)--> 新进程 INIT（天然回到基线）
任意状态 --(busy)--> 本轮跳过（不采样、不计时）
```

### 参数表

| 参数 | 值 | 说明 |
|---|---|---|
| SOFT_THRESHOLD | 基线 + 24MB | 软释放触发 |
| HARD_THRESHOLD | 基线 + 48MB | 硬上限（自愈重启） |
| CHECK_INTERVAL | 60s | 采样周期 |
| CONFIRM_TIMES | 2 | 连续超阈值才重启（防抖） |
| MIN_RECYCLE_INTERVAL | 3600s | 重启最小间隔（防风暴） |
| BASELINE_DELAY | 启动后 45s | 首次采样（等初始化完全稳定） |
| 内存度量 | Windows: Commit(PagedMemorySize64)；Linux: statm RSS+VmSwap | 与"系统实际被占用"一致 |

## 4. 实施清单（文件/函数级）

| 文件 | 改动 |
|---|---|
| `ocr/engine.py` | `release_engine()` 末尾 `gc.collect()`——释放即回收（根因1修复） |
| `app.py` `_close_overlays` | 会话结束 `gc.collect()` + `QPixmapCache.clear()`（L1-b） |
| `app.py` `_preview_closed` 钩子 | 已关闭预览窗即时摘出 `_previews`（L1-c） |
| `app.py` 新增 `_soft_release()` | gc + QPixmapCache + 摘预览窗 + 释放引擎（L1 完整版，供看门狗调用） |
| `app.py` 新增 `_recycle_self()` | 派生 `[exe, --hidden, --resident, --recycle]`（DETACHED）→ **静默 quit()（不弹通知）** |
| `app.py` `_on_command` | 新增 `--recycle` 命令（自愈通道，供测试与手动触发） |
| `utils/memory_watchdog.py` 新增 | 看门狗本体：采样/基线/状态机/跨平台内存读取 |
| `main.py` | `--recycle` 参数：轮询等待旧实例管道消失（≤15s）再 listen，避免抢名 |
| `app.py` 启动接线 | SnapApp.__init__ 创建看门狗（once 模式禁用）；controller 增 `busy()` |

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 会话进行中重启打断用户 | busy() 硬条件：遮罩/结果窗/预览窗/设置窗任一可见，或 OCR 线程在跑 → 跳过本轮 |
| 重启丢剪贴板 | 退出路径已有 OleFlushClipboard 交接；X11 侧 600ms 延迟退出已有 |
| 重启风暴 | 双阈值确认 + ≥1h 最小间隔 + 重启后新进程基线天然重置 |
| once/单文件模式误重启 | once 模式直接不启动看门狗 |
| 软释放后 OCR 变慢 | 仅空闲时释放；下次识别自动重载（1.2s，一次性）；busy 时绝不释放 |
| 内存读数波动误判 | 度量用 Commit（比 WS 稳定）；基线取历史最低；连续 2 次确认 |
| 自身 PID 复用/管道竞态 | 新进程 --recycle 轮询等管道消失后再 listen；抢名失败自动重试 |

## 6. 验证计划

1. 修复后 5 轮 OCR：每轮后 Commit 应回落到 基线+模型(~15MB) 以内（根因1消除）。
2. `--recycle` E2E：运行中触发 → 新进程接管（托盘/热键可用）、旧进程退出、日志记录。
3. 看门狗单元级：阈值判定/busy 判定（合成状态）。
4. 回归：单元 18/18、探针套件、打包自检 12/12。

## 7. 验收标准

- 连续 100 轮混合会话（复制+OCR）后，空闲 Commit ≤ 基线 + 48MB（硬上限），
  软释放后稳态 ≤ 基线 + 24MB（软阈值）。
- 任意时刻用户呼出热键 → 遮罩即出（≤300ms 感知）；OCR 首字延迟不因治理劣化
  （引擎常驻为默认态，软释放仅发生在空闲且超压时）。
- 自愈重启全程 ≤3s，用户仅在托盘看到一条气泡通知。
